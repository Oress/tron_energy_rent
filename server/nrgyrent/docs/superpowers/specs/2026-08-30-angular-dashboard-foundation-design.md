# Angular Dashboard Foundation Design

## Objective

Build the first production-ready increment of a custom Angular dashboard for the
`nrgyrent` Spring Boot server. The increment provides a mobile-first application
shell, a shared global filter, and two independently paginated report tables:
"Заказы" and "Прибыль по пользователям".

The dashboard is built during the Maven lifecycle, copied into Spring Boot's
static resources, and packaged in the executable JAR. A single OpenAPI document
is the source of truth for generated Spring server interfaces/models and the
generated Angular client.

## Scope

This increment includes:

- A standalone Angular 22.1 application under `server/dashboard`.
- A `core`, `features`, and `shared` source layout.
- PrimeNG 22 components and Tailwind CSS 4 styling.
- A mobile-first application shell and a sequential report layout.
- A global filter with searchable user and group selectors, inclusive date-from
  and date-to fields, and explicit Apply and Reset actions.
- Server-side pagination for both report tables.
- One OpenAPI contract used to generate both backend and frontend types and API
  interfaces.
- Empty backend query implementations with explicit
  `//TODO: implement queries` markers.
- Maven generation, frontend build, version metadata generation, static resource
  copying, and JAR packaging.
- SPA navigation support that cannot intercept server API, webhook, actuator, or
  static-asset requests.

This increment excludes:

- SQL query implementation.
- JPA report queries.
- Authentication or authorization implementation.
- Automated tests, as explicitly requested.
- Dashboard reports other than Orders and User Profit.
- Sorting, exports, saved filters, live updates, and row actions.

## Technology Baseline

- Angular core 22.1.4 and Angular CLI 22.1.6.
- TypeScript 6.0.x and RxJS 7.8.x, within Angular 22 compatibility ranges.
- PrimeNG 22.1.0 with PrimeIcons 8.0.0.
- Tailwind CSS 4.3.3, `@tailwindcss/postcss` 4.3.3, and the PrimeUI Tailwind
  integration.
- OpenAPI 3.0.x and OpenAPI Generator 7.25.0.
- Java 21 and the repository's existing Spring Boot 3.4.5 baseline.
- `frontend-maven-plugin` and `maven-resources-plugin` for client build and
  packaging.

Dependency versions are recorded in `package-lock.json` and Maven properties so
local npm builds and Maven builds resolve the same toolchain.

## Repository and Ownership Boundaries

The Angular project lives at `server/dashboard`, next to the existing
`server/nrgyrent` Maven project. Existing untracked generated/cache artifacts in
that directory are not treated as authoritative source. Source configuration and
generated output boundaries are explicit:

- Handwritten Angular code: `server/dashboard/src/app`, excluding
  `src/app/core/api`.
- Generated Angular API client: `server/dashboard/src/app/core/api`.
- Shared OpenAPI source: `server/dashboard/openapi/nrgyrent-api.yaml`.
- Generated Java sources: `server/nrgyrent/target/generated-sources/openapi`.
- Handwritten Spring adapter/query code:
  `server/nrgyrent/src/main/java/org/ipan/nrgyrent/dashboard`.

Generated Java sources are never committed. The generated Angular client is
regenerated by `npm run generate-api`; its directory contains a notice stating
that it must not be edited manually.

## Angular Architecture

The application uses standalone components, lazy feature routes, signals for
local state, and constructor-free `inject()` dependency access.

### Core

`src/app/core` contains application-wide infrastructure:

- `api/`: generated services, models, and client configuration.
- `guards/`: a clearly named placeholder route guard that currently permits
  navigation because Spring Security is not enabled. It does not pretend to
  provide security.
- `interceptors/`: an HTTP error interceptor that converts failed report loads
  into a stable user-facing error state while preserving the original error.
- `layout/`: the application shell and compact mobile header.
- `providers/`: API base-path configuration. Development requests use the
  Angular proxy; packaged requests use the same origin.

### Features

`src/app/features` owns business-facing behavior:

- `dashboard/`: lazy route and composition of the filter, Orders table, and User
  Profit table in that order.
- `dashboard-filter/`: draft and applied filter state, selector loading, date
  validation, Apply, and Reset behavior.
- `orders/`: Orders report component, server pagination state, loading state,
  empty state, and request-error state.
- `user-profit/`: User Profit report component with the same independent state
  boundaries.

The applied global filter is exposed as a read-only signal by a feature service.
Each report reacts to a new applied-filter revision, resets its offset to the
first page, and requests its own data. Changing draft controls causes no network
request. Apply submits the draft. Reset clears the draft and immediately applies
the empty filter.

If both user and group are selected, both parameters are sent and the eventual
SQL implementation must apply intersection semantics.

### Shared

`src/app/shared` contains presentation primitives with no dashboard-specific data
access:

- A TRX amount pipe that formats decimal TRX values and displays an em dash for
  absent values.
- Reusable empty and load-error presentation.
- Small pagination event types/utilities shared by the report components.

## Mobile-First Presentation

The page starts as a single compact column and progressively increases spacing
and typography at larger breakpoints. Filters stack vertically on narrow screens
and use a multi-column layout when space permits.

The reports remain semantic PrimeNG tables at every viewport. Financial and
audit columns are never hidden. Each table is placed in an intentional horizontal
scroll container with a sticky first identifying column, compact cells, visible
scroll affordance, and touch-friendly paginator controls. This preserves all 19
and 12 columns without converting rows into ambiguous cards.

Each report has its own paginator with page-size choices 10, 20, and 50. The
initial size is 20. API page indexes are zero-based. A failed request in one table
does not prevent the other table from rendering or paging.

## OpenAPI Contract

The contract base path is `/api/v1/dashboard`. Operations are grouped by stable
tags so OpenAPI Generator produces focused interfaces/services.

### Filter options

- `GET /filters/users` returns `FilterOption[]`.
- `GET /filters/groups` returns `FilterOption[]`.
- `FilterOption` has required `id: int64` and `label: string` fields.

Both backend option methods return empty lists and contain
`//TODO: implement queries`.

### Orders

`GET /orders` accepts:

- `page`: optional non-negative integer, default 0.
- `size`: optional integer from 1 through 200, default 20.
- `userId`: optional int64.
- `groupId`: optional int64.
- `dateFrom`: optional ISO local date, inclusive.
- `dateTo`: optional ISO local date, inclusive.

An Orders row has these required fields unless the source value is genuinely
nullable:

| UI column | Contract field | Type |
| --- | --- | --- |
| ID | `id` | int64 |
| Дата | `date` | ISO date-time |
| Логин | `login` | string, nullable |
| Имя | `name` | string, nullable |
| Тип Баланса | `balanceType` | string |
| Кол. транзакций | `transactionsCount` | int32 |
| Энергия всего | `totalEnergy` | int64 |
| Тариф | `tariff` | string, nullable |
| Провайдер | `provider` | string, nullable |
| Комиссия | `commission` | decimal TRX |
| Доход | `income` | decimal TRX |
| Реф. отчисления | `referralDeductions` | decimal TRX |
| Остаток от реф. отчисл. | `referralDeductionsRemainder` | decimal TRX |
| Прибыль | `profit` | decimal TRX |
| Активация кош. | `walletActivated` | boolean |
| Статус | `status` | string |

| № заказа | `orderNumber` | string, nullable |

“Остаток от реф. отчисл.” and “Прибыль” are separate columns, producing 19

### Page envelope

Each report returns a dedicated generated page model containing required:

- `content`: array of the corresponding row type.
- `page`: zero-based current page.
- `size`: effective page size.
- `totalElements`: total matching rows.
- `totalPages`: total matching pages.

OpenAPI decimal values map to Java `BigDecimal` and TypeScript `number`. The API
boundary always uses human-readable TRX decimal amounts, never raw SUN integers.
Future SQL must perform exact conversion from SUN to TRX before constructing the
response DTO.

## Backend Adapter and Query Placeholders

OpenAPI Generator creates Spring interfaces and models during Maven's
`generate-sources` phase. Handwritten REST adapters implement the generated
interfaces, normalize missing pagination defaults, and delegate to
`DashboardQueryService`.

The query service exposes one method per report and one per selector source. It
does not inject JPA repositories. For this increment every method contains the
exact comment `//TODO: implement queries` and returns a structurally valid empty
response. Pagination inputs are bounded to page 0 or greater and size 1 through
200 so the later plain-SQL implementation has stable invariants.

The eventual implementation is expected to use parameterized plain SQL, with a
data query and matching count query for each report. No partial SQL, example SQL,
or JPA substitute is introduced now.

## Existing Webhooks and Server Routes

The existing listeners are immutable for this increment:

- `POST /api/itrx/callback`
- `POST /api/trxx/callback`

Their controller classes, paths, headers, signature verification, payload
handling, and response behavior are not modified.

Dashboard endpoints live under `/api/v1/dashboard`, so they do not collide with
the webhook paths. SPA fallback handles extensionless browser navigation only.
It explicitly excludes `/api/**`, `/actuator/**`, and requests for files with an
extension. Missing API and webhook routes therefore remain server-side 404s and
can never be rewritten to `index.html`.

## Error Handling

The contract documents successful responses and standard 400 and 500 error
responses. Invalid pagination or date ranges return 400. The filter prevents an
end date earlier than the start date before issuing requests.

On the client, each report independently tracks loading, data, and a concise
Russian error message. A retry action repeats the last applied request. Empty
successful responses show “Нет данных.” Global selector-loading failures leave
the date controls and unfiltered Apply action usable.

## Build and Packaging

Maven performs this ordered pipeline:

1. Generate Spring interfaces/models from the dashboard OpenAPI document into
   `target/generated-sources/openapi`.
2. Install the configured Node.js and npm versions in the Maven build directory.
3. Run npm dependency installation in `../dashboard`.
4. Run `npm run generate-api` against the same OpenAPI document.
5. Generate `src/environments/version.ts` using Maven project version and the
   abbreviated Git commit when available.
6. Run the configured Angular production build.
7. Copy `../dashboard/dist/dashboard/browser` to
   `${project.build.directory}/classes/static` in `process-resources`.
8. Package the static files in the executable Spring Boot JAR.

`angular.build.skip` disables Angular-specific generation/build/copy executions
without disabling Maven's ordinary resource processing. Local development uses
an Angular proxy for `/api`; the packaged application uses same-origin relative
URLs.

## Verification Without Tests

No automated tests or test configuration are added. Completion requires these
direct verification checks:

- Validate the OpenAPI document.
- Generate both contracts without errors.
- Inspect generated Java and TypeScript models for identical names, nullability,
  page fields, and TRX-compatible numeric mappings.
- Complete an Angular production build.
- Compile and package the Maven project.
- Inspect the JAR for `BOOT-INF/classes/static/index.html` and hashed frontend
  assets.
- Audit Spring request mappings to confirm both webhook mappings are unchanged
  and dashboard routes use only `/api/v1/dashboard/**`.
- Confirm no query SQL or JPA report implementation was introduced and every
  placeholder method contains `//TODO: implement queries`.

## Acceptance Criteria

- Opening the packaged server root loads the Angular dashboard shell.
- The global filter supports user, group, inclusive date range, Apply, and Reset.
- Apply and Reset reset both report paginators and issue one request per table.
- Orders renders exactly 19 agreed columns and User Profit renders exactly 12.
- Both tables paginate independently through generated Angular services.
- All monetary values are treated and displayed as decimal TRX.
- Empty placeholder responses render cleanly without runtime errors.
- Backend and frontend types are generated from one OpenAPI document.
- The Angular build is present in the executable JAR.
- Existing ITRX and TRXX webhook behavior and mappings are unchanged.
- There are no report queries and no automated tests in this increment.
